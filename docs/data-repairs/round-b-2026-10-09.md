then, so it ran a full build. Checked against the byte-exact `fd74bec9` copy taken the night before:
all 60 tables identical row for row in the same physical order, `sqlite_master` identical (60

and the header's change counter went from 1636 to 1637, because the build deletes and re-inserts the
129 weights and the 10,020 library names from the same files. `shasum` hashes the FILE, not the
content, which is why the fingerprint moved when the content did not. Andy's ruling: record
`430ad7bf` and carry on. Fixed in `c0745e5`: `build_db.py` reads its arguments before it opens
anything and refuses an existing live database without `--i-mean-live`, the guard sweep in
`tests/test_live_guards.py` now covers it, and `CLAUDE.md` says never to run a script against live to
read its help.

## The rollback, as written

**The data and the code go back together, data first, with `:8000` stopped for the whole of it.**
Neither half is a rollback on its own: `766f2e3` against the new data prints 10 sized and
per-person rows wrong at every factor but 1x.

```sh
kill "$(lsof -t -iTCP:8000 -sTCP:LISTEN)"                     # :8000 only, found by its port
cp backups/recipes-20261009-234157.db recipes.db              # a whole-file restore, never re-inserted rows
shasum -a 256 recipes.db backups/recipes-20261009-234157.db   # both must read 430ad7bf...
cd ../recipe-app-serve && git checkout --detach 766f2e3 && npm run build
env -u DATABASE_URL nohup python3.13 scripts/serve_live.py > /tmp/serve8000.log 2>&1 & disown
lsof -a -p "$(lsof -t -iTCP:8000 -sTCP:LISTEN)" -d cwd -Fn     # must name recipe-app-serve
```

Then reload every open tab by hand. `766f2e3` sends no commit, so a tab on `59ba639` hears nothing
and shows no bar. This round inserted 8 ingredient rows and 2 notes and deleted 24 rows, so rows put
back by hand would get new ids and every baseline entry naming an id would be wrong. The restore is
the whole file or nothing. Anything written to live between the backup and a restore is lost by the
restore.
