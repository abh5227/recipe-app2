What it does, in one sentence each:

  `apply_amount_plan`): the author's second amount read off `raw_text` into `secondary_measure`,

  a compound amount joined so both halves scale, a size put back with the words it sizes, and 7
  broken amounts repaired where one reading is clearly proved.
- **the six rules the click-through added**: a sized piece is the amount (7 rows), an "or" count of

- **revision 2**: an "or" count of the same food is a second amount line keeping its "or", a count
  with an "or" inside it stacks as two lines, and an "or" count of a different food goes to the
  note (4 rows change). "plus more" remarks move to the note (74 rows, and 4 lines that run another
  ingredient into the remark go to the review list). The amounts in a note that opens
  "or <amount>" scale on the page, display only.
- **the joins**: 5 rows that are the rest of the row above them or only the measure of it, plus 3
  joins Andy decided from the residual list.
- **revision 3**: the four "plus more" lines revision 2 sent to review. garlic-kale 3861 stays one
  row with "~2 small lemons" as its second amount and "plus more for massaging kale" as its note.

  from the recipe on six other lines.
- **the code**: Edit mode's second amount behind a small arrow beside the amount (C1), and a quiet

- **the calls**: hummus-2's garnish line becomes an ingredient heading with three garnishes under

**545 writes over 186 recipes, 962 cells over 580 rows, 24 rows deleted and 9 inserted.** 29 rows

⚠️ **THE ORDER IS CODE FIRST, AND REVISION 2 FOUND IT IS A FENCE FOR TEN ROWS.** The round adds no
column and drops none, so both schemas stay at migration 63. The new code against the OLD data reads
`secondary_measure` and prints whatever is in it, which on the old data is the old meaning (a copy of
the first amount on 130 rows, a value carrying a stray leading slash on 82 more). That reads oddly
for the minutes between the deploy and the pass, and it does not fail.

The OLD code against the NEW data is not safe at every factor. It has no rule for a sized piece or a
per-person amount, so at 2x it prints "2-inch knob" for hainanese's "1-inch knob" and "about 1 cup
per person" for "about ½ cup per person". Measured with 766f2e3's own `amountText` over the rehearsed
copy: 10 rows, 7 sizes and 3 per-person amounts, wrong at every factor other than 1x. So the data
waits for the code, and the code is not live until every open tab has loaded it.

⚠️ **AN OPEN TAB KEEPS THE BUNDLE IT LOADED.** Andy's revision 1 click-through ran a8ba985's bundle
against revision 1's server and data. The :8002 log shows his tab never fetched the new bundle after
the restart, and that is how "about ½ cup per person" doubled on his screen. A restart reaches the
server and not the page already open.

⚠️ **THE RELOAD BAR CANNOT HELP THIS GO-LIVE.** From this round on, the server names its commit on
every API answer and writes it into the page it serves, and an open tab shows a quiet bar when the
two differ. Tabs already open on `766f2e3` carry no such check, so this go-live still needs every open
tab reloaded by hand before the data step, proved by the server log (step 3). From the next update
on, the bar does it. ⚠️ **A ROLLBACK TO `766f2e3` IS SILENT IN THE SAME WAY.** That server sends no
commit, so a tab on the new code hears nothing and shows no bar. After a rollback, reload every tab
by hand again.

## 4. The data step

```sh
SP=<a scratch directory>
LIVE=recipes.db
cp "$LIVE" "$SP/before.db"                                   # copy, never symlink
python3.13 scripts/gates/state.py --db "$SP/before.db" --out "$SP/before.json"

python3.13 scripts/apply_round_b.py "$LIVE" --i-mean-live    # the DRY RUN, always first
python3.13 scripts/apply_round_b.py "$LIVE" --apply --i-mean-live

cp "$LIVE" "$SP/after.db"
python3.13 scripts/gates/state.py --db "$SP/after.db" --out "$SP/after.json"
python3.13 scripts/gates/rounds.py --round golive/rounds/2026-10-08-round-b.json \
  --before "$SP/before.json" --after "$SP/after.json" \
  --a-db "$SP/before.db" --b-db "$SP/after.db"
python3.13 scripts/gates/cells.py --a "$SP/before.db" --b "$SP/after.db" \
  --round golive/rounds/2026-10-08-round-b.json
```

Read the dry run against the declaration before typing `--apply`. Both gates must print their own
sentence and exit 0:

```
THE ROUND DID EXACTLY WHAT IT DECLARED
EVERY MOVED CELL WAS DECLARED
```

⚠️ **THE PASS GATES EVERY RECIPE BEFORE IT COMMITS.** Each recipe is its own transaction, and its
annotation set and its byte-equal place are read before and after inside that transaction. A failure
therefore stops at one recipe with the ones before it already committed, and the message says which
those are. That is deliberate: a gate run over the whole pass would be a post-mortem on data already
on disk.

⚠️ **THE PASS STOPS BEFORE ITS FIRST WRITE IF THE RESIDUAL LIST HOLDS ANSWERS NO COMMIT HAS.** Every
run rewrites `reports/round-b-residual-2026-10-08.csv`, the dry run included. If DECISIONs have been
typed into that file and not yet copied into a committed decisions file, the pass names the rows and
exits, and nothing has been written. Revision 2's answers to the four "plus more" lines were lost to
exactly that overwrite. Commit the answers, or move the file aside, then run again.

⚠️ **AND A SECOND RUN WRITES NOTHING.** Measured on the rehearsal: the second run prints "nothing to
do. Every decision is already in place." Re-running after a stop is safe, though it will stop in the
same place until the cause is fixed.

## 6. Rollback: the data AND the code, together

A rollback restores both halves, data first, with `:8000` stopped for the whole of it. Neither half
is a rollback on its own. The old code against the new data prints 10 sized and per-person rows
wrong at every factor but 1x (see the top of this plan). The new code against the old data reads it,
and leaves the round half undone.

```sh
kill "$(lsof -t -iTCP:8000 -sTCP:LISTEN)"                 # :8000 only, as in step 3
cp backups/recipes-<stamp>.db recipes.db                  # the data: a whole-file restore of step 0's backup
shasum -a 256 recipes.db backups/recipes-<stamp>.db       # must match, and must be step 0's sha
cd ../recipe-app-serve && git checkout --detach 766f2e3 && npm run build   # the code: today's commit
nohup python3.13 scripts/serve_live.py > /tmp/serve8000.log 2>&1 & disown
lsof -a -p "$(lsof -t -iTCP:8000 -sTCP:LISTEN)" -d cwd -Fn   # must name recipe-app-serve
```

**Then reload every open tab by hand.** `766f2e3` sends no commit, so a tab on the new code hears
nothing and shows no reload bar. The server log proves it, as in step 3.

⚠️ **THERE IS NO REVERSE PASS AND THERE CANNOT BE ONE.** The round deletes 24 ingredient rows and
inserts 9, and an insert mints a new id. Re-inserting a deleted row by hand gives it a different id,
and every baseline entry naming the old one is then wrong. 545 writes come back from the backup or
not at all. Anything written to live between the backup and the restore is lost by the restore, so
keep the two close together.
