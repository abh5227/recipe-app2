# Go-live: round B

The round's declaration is `golive/rounds/2026-10-08-round-b.json` and the gate is held to that file
and nothing else. The decisions it reads are
`docs/data-repairs/round-b-decisions-2026-10-08.csv`, 37 rows, committed before anything read them.

What it does, in one sentence each:

- **the rules** (`import_cleanup.amount_plan`, which the importer calls through
  `apply_amount_plan`): the author's second amount read off `raw_text` into `secondary_measure`,
  a unit or a measure or a number word or a piece of punctuation taken out of the front of a name,
  a compound amount joined so both halves scale, a size put back with the words it sizes, and 7
  broken amounts repaired where one reading is clearly proved.
- **the joins**: 5 rows that are the rest of the row above them or only the measure of it.
- **the calls**: hummus-2's garnish line becomes an ingredient heading with three garnishes under
  it, beans' 15-row simmer-time chart becomes one note linked to step 1783, flatbreads row 3824
  splits into two ingredients, and miso-tofu row 9135 keeps its 16 oz and sends "block" to the
  second amount.

**443 writes over 155 recipes.** 36 rows are flagged and left exactly as they are, 24 of them
because the cook has edited that row.

⚠️ **THE CODE AND THE DATA ARE SEPARABLE, AND THE ORDER IS CODE FIRST.** The round adds no column
and drops none, so both schemas stay at migration 63. The new code reads `secondary_measure` and
prints whatever is in it, which on the old data is the old meaning (a copy of the first amount on
130 rows, a value carrying a stray slash on 163 more). That reads oddly for the minutes between the
deploy and the pass, and it does not fail. The old code against the NEW data ignores the column
entirely, because no old client read it. So the code may go first and the data may wait. Applying
the data first leaves the old client showing nothing new, which is also safe, and that is what makes
this round's order a preference rather than a fence.

## 0. Before anything

```sh
python3.13 backup.py                      # then read the backup's sha256 AND live's. They must match.

git fetch origin && git rev-parse origin/main
echo "DATABASE_URL=[${DATABASE_URL-}]"    # must print []
```

The backup is the data rollback. A backup nobody fingerprinted is a hope.

## 0b. The CI-condition run, from a FRESH CLONE


⚠️ **A LINKED WORKTREE IS NOT THIS CONDITION.** `corpus_guard.live_db()` finds the main working tree
through `git rev-parse --git-common-dir`, so from a worktree the real database is still live, the 7
`live_catalog` tests still run against it, and six guard tests fail for that reason alone.

**The Postgres leg is not required for this round.** It touches no `migrations/*.sql` and no
`alembic/`, so there is no second schema to compare. The command is in `golive/README.md` if
anything about that is in doubt.

## 4. The data step

```sh
SP=<a scratch directory>
LIVE=recipes.db
cp "$LIVE" "$SP/before.db"                                   # copy, never symlink
python3.13 scripts/gates/state.py --db "$SP/before.db" --out "$SP/before.json"

python3.13 scripts/apply_round_b.py "$LIVE" --i-mean-live    # the DRY RUN, always first
python3.13 scripts/apply_round_b.py "$LIVE" --apply --i-mean-live

cp "$LIVE" "$SP/after.db"
python3.13 scripts/gates/state.py --db "$SP/after.db" --out "$SP/after.json"
python3.13 scripts/gates/rounds.py --round golive/rounds/2026-10-08-round-b.json \
  --before "$SP/before.json" --after "$SP/after.json" \
  --a-db "$SP/before.db" --b-db "$SP/after.db"
python3.13 scripts/gates/cells.py --a "$SP/before.db" --b "$SP/after.db" \
  --round golive/rounds/2026-10-08-round-b.json
```

Read the dry run against the declaration before typing `--apply`. Both gates must print their own
sentence and exit 0:

```
THE ROUND DID EXACTLY WHAT IT DECLARED
EVERY MOVED CELL WAS DECLARED
```

⚠️ **THE PASS GATES EVERY RECIPE BEFORE IT COMMITS.** Each recipe is its own transaction, and its
annotation set and its byte-equal place are read before and after inside that transaction. A failure
therefore stops at one recipe with the ones before it already committed, and the message says which
those are. That is deliberate: a gate run over the whole pass would be a post-mortem on data already
on disk.

⚠️ **AND A SECOND RUN WRITES NOTHING.** Measured on the rehearsal: the second run prints "nothing to
do. Every decision is already in place." Re-running after a stop is safe, though it will stop in the
same place until the cause is fixed.

**The data:** a whole-file restore of step 0's backup, and only that.

```sh

cp backups/recipes-<stamp>.db recipes.db
shasum -a 256 recipes.db backups/recipes-<stamp>.db      # must match
```

⚠️ **THERE IS NO REVERSE PASS AND THERE CANNOT BE ONE.** The round deletes 21 ingredient rows and
inserts 4, and an insert mints a new id. Re-inserting a deleted row by hand gives it a different id,
and every baseline entry naming the old one is then wrong. 443 writes come back from the backup or
not at all. Anything written to live between the backup and the restore is lost by the restore, so
keep the two close together.
