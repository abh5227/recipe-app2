# Chef's Choice

A personal recipe app for one household. It holds 300 recipes with their method steps, an
itemized **plan ahead** panel for the waiting a recipe needs, star ratings gated behind actually
cooking the thing, a cook log with photos, and quantity scaling that converts volumes to weights.
Recipe lines can link to a shared ingredient library built from public food vocabularies. It runs
on your own machine and is gated behind a login.

The point of it is the **outcome data**. Recipes are easy to find anywhere. What gets cooked, how
it was rated, and how a person changed it are not, and that is what this records.

> `OVERVIEW.md` is the two-minute orientation. `CODE_WALKTHROUGH.md` is the guided tour of the code
> and the living history of why it is built this way. `CLAUDE.md` holds the standing rules that
> govern changes to it. This file is how you set it up, run it, and work on it safely.

## Setting it up from a fresh clone

You need **Python 3.12 or newer** and **Node 22 or newer**. CI builds on Python 3.12 and Node 24,
and a fresh clone is proven to work offline with nothing else installed.

```bash
python3.13 -m pip install -r requirements.txt   # flask, flask-login, SQLAlchemy, alembic,
                                                #   psycopg, pillow, pillow-heif
npm install                                     # Vite (the build) and TipTap (the step editor)
npm run build                                   # builds the frontend into dist/
python3.13 build_db.py                          # applies the 59 migrations, loads the seed data
python3.13 app.py                               # serves on http://localhost:8000
```

`npm run build` is **required**, not optional. Flask serves `dist/index.html` at `/`, so skipping
it gives you a 500 on the front page. Rerun it after editing anything in `static/`.

### Then make yourself an account

⚠️ **You cannot sign up through the app on a fresh install.** `/api/signup` always requires an invite
code, and on a new database there is nobody to issue one, so the page loads and nothing lets you in.
The first account is made from the command line:

```bash
python3.13 scripts/create_admin.py            # prompts for an email and a password
```

The password is read with `getpass`, so it never lands in your shell history or the process list.
After that, log in at the page and invite anyone else from inside the app.

**If a fresh install fails partway through migrating, delete the new `recipes.db` and run it
again. A fresh install has no data to lose.**

A fresh clone has no recipes in it. `seed.py`'s recipe and ingredient lists are both empty on
purpose, so `build_db.py` creates the schema, loads the King Arthur weight chart, and stops. The
300 recipes live in `recipes.db`, which is not in git. See **Where the live database lives**.

### The one optional file

Linking a recipe line to the ingredient library is **off until you place one file**:

```text
library_names.csv     library_id, canonical, commonality. About 400 KB, 10,020 rows.
                      Generated by build_library.py. Git-ignored, placed by hand.
```

**A fresh clone does not have it, and that is expected.** Without it the lookup table is empty, the
app runs normally, and the linking feature never fires. Nothing errors. Drop the file in the project
folder and rerun `build_db.py` to switch it on. Generating it yourself needs `join.db` and
`sources.db`, two large vocabulary databases that are also not in git, and if you do not have those
then you do not need this file.

## Running it

There are three ways to run this, and they are not interchangeable.

### Your own machine, for a look

```bash
python3.13 app.py          # :8000, serving the shared dist/
```

Fine for a fresh clone with no data. **Do not use this to serve the real database.**

### Frontend work, with hot reload

```bash
npm run dev                        # Vite on :5173 — this is the one you open
FLASK_DEBUG=1 python3.13 app.py    # Flask on :8000, serving /api, /images and /fonts
```

Open **:5173**, not :8000. Vite serves `static/` directly and reloads on save, so `npm run build`
is not needed in this loop. `FLASK_DEBUG=1` restarts Flask when a `.py` file changes and turns on
its error pages. It is off by default so the plain `python3.13 app.py` above is an ordinary server.

### The real one, from a pinned checkout

⚠️ **:8000 never serves the shared `dist/`.** The live server runs from its own git worktree,
pinned to a commit that has been pushed, with its own `dist/` that no build in the working repo can
reach:

```bash
git worktree add ../recipe-app-serve <pushed-sha>
cd ../recipe-app-serve && npm install && npm run build
python3.13 scripts/serve_live.py            # :8000, against the REAL database and photos
```

`serve_live.py` points that pinned checkout at the real `recipes.db` and the real photo folder by
rebinding module globals, and it finds them through git rather than by a hardcoded path. The bundle
and the server are therefore the same commit by construction while the data stays live. It
**refuses to run from the main working tree**, because doing that is exactly what the rule
forbids.

*Why this exists:* `dist/` is rebuilt by every `npm run build`, including the ones behind a preview.
A preview build once put a client that sends `{id, text}` steps in front of a server old enough to
read a non-string step as `""`, which would have blanked every method step of the first recipe
saved, with a 200 and no sign anything was wrong.

**After any push you want live to run, rebuild the pinned worktree at the new commit.** Do not point
:8000 at the working tree just this once.

## Where the live database lives, and how the guard finds it

The live database is `recipes.db` in the project folder. It is git-ignored, it is about 330 MB, and
it holds everything that cannot be regenerated: the 300 recipes, 137 cook-log entries, the ratings,
the photos' records, and the per-recipe baselines the "your changes" view is diffed against.

Every script that can write **names its database as an argument, defaults to a dry run, and refuses
the live one without `--i-mean-live`**. The one definition of "this is live" is
`scripts/corpus_guard.py`, and every caller imports it rather than keeping a copy.

**The guard identifies the file, not the spelling of its name.** It compares the resolved path AND
the device and inode, so `./recipes.db`, `scripts/../recipes.db`, a symlink and a hard link are all
one answer. A string comparison let three of those four through.

**And it gives the same answer from every checkout.** `corpus_guard.live_db()` resolves the live
path once, in this order:

1. `$RECIPE_APP_LIVE_DB`, an absolute path, for an unusual layout or a test.
2. `~/.config/chefs-choice/live-db`, one line holding that path, read by every checkout.
3. **git**, which is the normal answer. A linked worktree's common git dir is the main checkout's
   `.git`, so its parent is the main working tree.

If none of the three answers, the guard **fails closed**: every path is treated as live, so a write
needs the sentence typed out. This matters because the pinned `../recipe-app-serve` is itself a
worktree whose whole job is to run against live, and an earlier guard that asked its own checkout
answered "not live" from there and refused nothing.

**The test suite cannot open the live database at all.** `tests/dbguard.py` patches `sqlite3.connect`
when `conftest` is imported, which covers raw connections, SQLAlchemy and the app's own session
factory with one patch. The only exceptions are `@pytest.mark.live_catalog` and
`@pytest.mark.live_schema`, and both may open it **read-only** and nothing more.

## Rehearsing on a copy

Any data repair is rehearsed on a copy of live first, and the whole chain is run from a clean
checkout before it is run for real. A pass applied on its own to a corpus already part way through
agrees with the chain by luck.

```bash
cp recipes.db /tmp/rehearse.db                 # copy, NEVER a symlink
DB=/tmp/rehearse.db

python3.13 migrate.py --db "$DB"
python3.13 scripts/apply_plan_ahead_proposals.py "$DB" --apply
python3.13 scripts/add_missed_waits.py "$DB" --apply
python3.13 scripts/convert_step_headings.py "$DB" --apply
python3.13 scripts/apply_label_rules.py "$DB" --apply
```

The order matters. Each pass reads what the one before it left, and
`docs/data-repairs/README.md` is the index that says so.

⚠️ **During a rehearsal, never type the live path. Use the copy's path.** The guard is the backstop,
not the plan. Pointing a script at `recipes.db` "to test the guard" is how live gets opened, and it
has happened.

Running the same chain against live means adding `--i-mean-live` to every line, and that is a
sentence a person has to type on purpose.

**A dry run never writes into `docs/data-repairs/`.** Reports go to the git-ignored `reports/`
folder. `--record` is what puts one in the committed folder, and it refuses to overwrite a non-empty
file. Five scripts once wrote their report on every run and truncated three committed records to
their header lines, from dry runs.

**Every corpus pass patches the live row and the `reason='original'` baseline in one transaction.**
The "your changes" view is the difference between that baseline and the current rows, so a pass that
rewrote a row without rewriting the baseline would be indistinguishable from the cook having edited
it by hand. That lockstep is what let 300 recipes be restructured while the 49 real annotation
entries stayed at 49.

## Backups

```bash
python3.13 backup.py        # timestamped copy into backups/
```

`recipes.db` is the one irreplaceable file here. The ratings, the cook history and the photos exist
only in it, and it is not in git. Run `backup.py` before anything risky. It keeps the most recent 30
timestamped copies and prunes older ones.

⚠️ **The prune glob is `recipes-[0-9]*.db`, which is deliberate.** A backup you want kept
permanently should be named so that glob cannot match it. The go-live rollback copy,
`backups/recipes-golive-pre055-20261001-123825.db`, is named that way on purpose: it is the state of
live immediately before the first write of the go-live window, and `backup.py` can never prune it.

An earlier version of the prune matched `recipes-*.db`, which also caught hand-named
`recipes-preview-*.db` copies. Digits sort before letters, so a fresh backup sorted first and was the
first thing deleted. That function destroyed its own output on every run.

⚠️ **There is no off-machine copy of the backups or the photos yet.** `static/images` exists only on
this Mac. See the open decision in `ROADMAP.md`.

## Migrations

The schema is the `migrations/` folder, applied in filename order. There are 59 files. Add a new
numbered file rather than editing an existing one. `migrate.py` records what it has applied in
`schema_migrations` and only applies what is new, so re-running it is safe, and it changes the
database in place rather than rebuilding it.

`migrate.py` tracks applied work **by filename only**, with no checksum. Editing an applied file
therefore neither re-runs it nor is rejected, and nothing detects an edit that diverges from what
actually ran. A correction goes in a later migration.

**A table rebuild is one transaction.** `migrate.py` applies each file with `executescript`, which
opens no transaction, so every statement auto-commits on its own. A create-copy-drop-rename
interrupted in the middle is committed half done, and the dangerous shape is the quiet one: truncated
before its `CREATE INDEX`, the rebuild looks finished and the indexes are simply missing. The six
rebuild migrations carry their own `BEGIN;` and `COMMIT;`, and a test states that rule over the whole
folder so the next one is covered. ⚠️ Do **not** lift the wrap into `migrate.py` as a blanket rule. A
`PRAGMA foreign_keys` is a silent no-op inside a transaction, and migration 045 sets it off for its
rebuild and back on after, so a central wrap would disarm the one file that needs it.

`alembic/` owns the Postgres schema and `migrations/` is the SQLite half. The two are written by hand
from the same intention, and `tests/test_schema_parity.py` is what keeps them honest.

### The order rule, against a deploy

⚠️ **A migration's order against the deploy follows its direction. Additive goes BEFORE the deploy,
destructive goes AFTER.** The question is which of the two versions names something the other side
does not have.

- Migration 053 **added** `recipe_waits.step_id` and the new code selects it, so deploying first
  would have failed every recipe page on a column that did not exist yet.
- Migration 054 **dropped** two columns the old code still declared on its model, so migrating first
  would have failed every recipe page the other way.

Same outage, opposite order. The rule underneath both is to find the version that can serve **both**
schemas and run that one in the middle. Verify it rather than reasoning it out: start the intermediate
version against the current schema and confirm the pages build before touching the schema.

*Corollary for a drop:* retire the column in one commit, stop reading and writing it while leaving it
in the table, and drop it in a later one. That makes the deploy-then-migrate order available instead
of forcing a simultaneous cutover.

## Tests

```bash
python3.13 -m pip install -r requirements-dev.txt   # one-time: pytest
python3.13 -m pytest                                # the Python suite
node --test tests/js/*.test.js                      # the JS suite (zero dependencies)
```

Each test builds its own throwaway database from the migrations, so the suite never touches the real
one. The JS suite runs on the source with no `node_modules`.

**The Postgres suite is a separate run, and it must be.** A Postgres `DATABASE_URL` sends the SQLite
fixtures to Postgres and breaks them, so the two are different steps:

```bash
# start the container, or reuse it if you already made one
docker start pgci 2>/dev/null || \
  docker run -d --name pgci -p 55432:5432 -e POSTGRES_HOST_AUTH_METHOD=trust postgres:16

# the DATABASE must exist before alembic can put a schema in it. Once per container.
docker exec pgci createdb -U postgres recipe_test

DATABASE_URL=postgresql+psycopg://postgres@127.0.0.1:55432/recipe_test \
  SECRET_KEY=ci-only-not-a-real-secret \
  sh -c 'alembic upgrade head && python3.13 -m pytest tests/test_pg_integration.py tests/test_schema_parity.py'
```

`createdb` is a separate step on purpose. `alembic upgrade head` creates the schema INSIDE a
database and cannot create the database itself, so skipping it fails with
`database "recipe_test" does not exist`. A `SECRET_KEY` is required rather than optional: a Postgres
`DATABASE_URL` makes the app fail closed without one. See `docs/SECURITY.md`.

`tests/test_schema_parity.py` runs **only** here, because comparing the two schemas needs both of
them present. In the SQLite run its Postgres tests skip.

### The CI condition

⚠️ **"Green locally" is meaningless if the suite is quietly reading the real `recipes.db`.** CI has no
`recipes.db`, so reproduce that before trusting a green run, especially after changing how code
reaches the database:

```bash
mv recipes.db recipes.db.hidden && python3.13 -m pytest ; mv recipes.db.hidden recipes.db
```

This caught a real defect once. A frozen-at-import engine bypassed the harness's redirect, so the
ORM silently queried the real database during tests. It passed locally, because the file existed and
its contents happened to match the fixtures, and failed in CI. A call-time session factory that reads
the redirected module global is the fix, and this is the standing guard.

### The one test that fails locally on purpose

`tests/test_mining_boundaries.py::test_a_catalog_canonical_is_food_unless_its_exact_form_is_listed`
**fails on this machine and skips in CI.** It is the Miracle Whip case. The test reads the real
10,020-entry library catalog, which only exists here, and asserts that a catalog name is a food
unless its exact form is listed as an exception. Under the CI condition there is no catalog to read,
so it skips.

So the expected result depends on which machine you are on:

| where | result |
|---|---|
| a fresh clone | **0 failed.** The catalog is empty, so every test that needs it skips |
| CI, with no `recipes.db` | **0 failed**, same reason |
| this machine, with the real data | **1 failed**, the Miracle Whip case, and that is expected |

Seven tests carry `@pytest.mark.live_catalog` for the same reason: a fixture database has the
catalog tables with no rows, so a check written only against one proves nothing. ⚠️ **"No catalog"
has to mean no ROWS, not no file.** Eight tests once went red on a fresh clone because they skipped
only when `recipes.db` was absent, and a clone has the file with none of the rows in it.

## The importer, in brief

The import path is three stages, so a new source never touches core logic:

```text
paprika_native_reader.py  ->  import_cleanup.py  ->  import_write.py
```

orchestrated by `import_runner.py`, which **writes only with `--yes`** and takes a backup first.
Imported recipes are written at the app tier, so a rebuild never touches them, and are de-duplicated
by their source `uid`.

The guiding rule is **decline over guess**. The importer extracts the clear cases, **flags** the
ambiguous ones to the `import_flags` review queue, and never silently mis-structures a recipe. In
particular:

- **A lead-in label becomes a heading** when it reads as a label. "Refuse a label with an unbalanced
  bracket" is a rule, as is refusing one that is really a clause, a sentence fragment, or more than
  six words.
- **When no rule can judge a label**, it is left as a step and flagged. "Salt lightly" and "Do a
  window pane test" look exactly like labels that were approved, and nothing about the label itself
  separates them. The signal is what follows: of 104 approved labels, 99 are followed by a capital,
  and a lowercase continuation means the author wrote one sentence with a colon in the middle.
- **A decision a person makes is recorded as data the corpus pass reads**, never as a hand edit to
  one row.

⚠️ **One rule set means one function.** The importer and the corpus pass call the same code for the
same decision. Both files once said they shared the rules and had drifted, and the corpus pass wrote
a heading reading `Wilt the [[spinach]]`, which the renderer escapes and never linkifies, so the
brackets would have printed.

## Fix by rule, not by row

Every data or display correction is written as a rule that runs over every existing recipe, runs in
the importer for new ones, and has tests. Where a rule cannot decide, it flags the recipe instead of
guessing, a person decides once, and that decision is recorded as data.

A hand-fixed row is invisible to the next import and to the next corpus pass, so the same defect
returns on the next recipe and nothing says it was ever decided.

## Where the decisions live

`docs/data-repairs/` holds 21 files of two different kinds, and the difference is whether code opens
them.

- **A recorded decision** is an input to a pass. It **must be committed**, because a pass that cannot
  be re-run from a fresh clone is a hand edit with more steps.
- **A review artifact** is the output of a one-time survey that nothing opens. It may stay untracked.

The test is mechanical: **if a committed `.py` opens the file, it is a decision and it is committed.**
`docs/data-repairs/README.md` is the index and says, per file, what reads it and whether it is
committed.

Other documents worth knowing:

```text
docs/measuring-the-premise.md       measure the shape of the data before writing the parser
docs/what-the-library-is-for.md     read before any rule that admits, cuts, renames or merges a row

docs/import-reference-15.md         the regression baseline for the 15 verified recipes
docs/SECURITY.md                    why a Postgres DATABASE_URL fails closed without SECRET_KEY
docs/estimating.md                  whose hours an estimate counts
```

## Working on it

The conventions that matter are in `CLAUDE.md`. The short version:

- **Conventional Commits.** `feat` for a new user-facing capability, `fix` for a bug fix, `chore` for
  routine groundwork, `docs` for documentation.
- **Commit onto `main`.** Side branches are where work gets forgotten.
- **Stage work in per-stage commits**, with both suites green at each one.
- **Add files to a commit by name.** `git add .` sweeps up whatever else is lying around, and in a
  repo whose working folder holds database copies and review artifacts that is how something private
  or enormous gets committed by accident.
- **Never push without asking**, and watch the GitHub Actions run to green afterwards.

```bash
git add app.py tests/test_the_thing.py       # by name, not git add .
git commit -m "fix: describe what actually changed"
git push                                      # only when asked
```

`recipes.db` is git-ignored, so pushing saves your code and not your data. That is why `backup.py`
exists separately, and why the off-machine copy in `ROADMAP.md` is still an open question.
